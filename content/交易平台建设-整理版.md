### 第一部分 · 业务模型与平台建设（顾德强 / 李超）

#### 1.1 业务背景

到店业务线：到餐、到综、住宿、门票

链路：平台 → 用户 → 商家

核心痛点：流程不统一、业务不统一、平台划分困难

多业务联合售卖：团购、拼团、秒杀、会员卡，关单时间不同

- 

解决思路：系统分层 + 数据模型设计 + 状态机流转

#### 1.2 交易理解

本质：买卖双方钱货（物品/服务）交换的行为

线下交易：买卖双方直接交换

线上交易：双边交易，两笔交易通过履约行为联动

用户 → 美团：下单（履约、购买）

美团 → 商家：上单

- 

商家 → 美团：结算

#### 1.3 领域划分（核心域 + 支撑域）

|||||
|---|---|---|---|
|核心域|订单域|生单、快照、取消、价格、限购、风控|用户和商家签订交易契约的过程（订单），关注怎么买、买什么、多少钱|
|核心域|履约域|发货/发码/出票、收货/验码/验票、退货/退码/退票|商家完成货的交换（履约单），关注货是什么、怎么发货、怎么消费、退货|
|核心域|售后域|退单、退款、原因、违约金|交易取消、违约金逆向处理（退款申请单），关注退多少、怎么退|
|支撑域|支付域|支付、退款、合单、转账、营销、积分|用户订单的付款和退款通道|
|支撑域|资金域|资金管控、清分流水、资金账户、资金明细|落地交易过程凭证，对各类资金管控与清分|


#### 1.4 数据模型

||||
|---|---|---|
|支付单|资金明细、订单-支付单|订单 1:N 支付单 1:1|
|订单|资金明细、购买项|履约单 N:1|
|履约单|消费项、资金明细|退款单 1:N|
|退款单|退款项、资金明细||


- 购买项 - 消费项 - 退款项：酒店-间夜、门票-票、团购-券
- 资金明细关联所有模型（收银台、立减、优惠券、积分、折扣卡）
支付复杂场景：
|||
|---|---|
|1 个订单单支付|1:1|
|多个订单合并支付|N:1|
|1 个订单多期支付（分期付）|1:N|


#### 1.5 平台实现方案

架构层次（业务身份 → 业务活动 → 领域能力 → 平台 SDK）：

||||
|---|---|---|
|业务活动|下单、消费、退款|流程可编排|
|领域能力|域服务 + 域能力 + 能力扩展点|差异分离|
|平台 SDK|业务插件|实现可扩展|
|业务身份|身份识别 + 业务请求|业务身份定义|


核心原则：业务身份定义、领域能力扩展、流程扩展、开发/发布/监控/测试全流程支持

#### 1.6 开发分离

问题：业务线代码跑在平台服务内，耦合严重

解决方案：

|||
|---|---|
|开发分离|平台与业务、业务与业务仓库独立|
|运行隔离|自定义类加载器避免类冲突；独立上下文避免 bean 冲突|
|域服务|服务代码 → 调用 → 扩展点接口定义 → 默认实现 / 业务实现|
|容器隔离|平台容器 + 各业务类加载器（appkey、URLClassLoader、classpath、jar 列表、context、annotation）|


#### 1.7 部署隔离

问题：业务迭代快，平台服务发布频繁；业务插件性能问题影响其他业务

方案：按业务维度分集群部署

```
业务编排层 (业务1/2/3/4)
      ↓ RPC
业务流量路由
      ↓
域服务 (应用层): 业务1集群、业务2集群、业务3集群、业务4集群、通用集群
      ↓
数据源/中间件路由
      ↓
DB / MQ / Cache (按业务分)
```

根据业务身份进行业务流量路由

- 

根据业务身份进行中间件流量路由

#### 1.8 监控定位

基本思路：在常规监控能力基础之上集成插件化定制信息

|||||
|---|---|---|---|
|能力 - 业务身份监控|监控插件关联的业务维度接口服务情况|业务全景链路（基于插件所在平台领域接口的黄金指标）|链路 Trace（集成插件扩展点的执行信息）|
|能力 - 扩展点监控|监控插件实现的扩展点执行情况|根因定位（基于插件维度的异常数据分析）||
|能力 - 资源占用监控|监控插件的内存、cpu 占用|||
|基础|日志埋点标准化、框架统一上报|||


#### 1.9 未来规划

短期：能力建设 + 质量建设
- 多品售卖能力、检索能力、秒杀能力等
- 性能提升、自动化测试

中长期：标准化、解决方案生态
- 能力标准化治理
- 面向业态的业务能力建设，端到端建设
- 扩展点/能力/流程的插件生态市场建设

平台规划 = 配置化 × 一体化 × 智能化

#### 1.10 Q&A

|||
|---|---|
|公司平台化过程中存在博弈，业务不用平台|① 组织原因：自下而上或自上而下发起；② 技术层面：能力沉淀多、分层差异复用，可先从底层（数据层）开始往上做|
|数据库表结构如何标准化|扩展表添加扩展数据，使用 json 的方式|
|数据如何迁移|交易数据不迁移，不同平台数据不一样|
|新老数据如何聚合|单订单查询无需聚合；多订单查询由单独服务支撑|


### 第二部分 · CRM 系统业务流程

#### 2.1 平台挑战

历史架构：烟囱式（餐 CRM + 酒 CRM + 综 CRM 各自独立）

业务规模：亿级线索资源，规则计算 10w 级 tps；30+ 业务线（餐、综、酒、门票、充电宝等）；10w+ BD/BDM/代理商/运营使用

业务诉求：能力快速复用、个性化支持、安全/稳定、多团队并行开发

平台能力要求：通用性、扩展性、可用性、可维护性

- 

核心问题：多业务如何高效、稳定地支持？

#### 2.2 平台建设思路

设计目标：通用性、扩展性、可用性、可维护性

设计原则：关注点分离 + SOLID 原则

架构思路：

|||
|---|---|
|数据模型|共性抽象统一，元数据扩展差异|
|流程逻辑|标准化、配置化|
|页面视图|组件化|
|应用架构|分层、插件化、可维护性|
|技术架构|多租户、业务隔离、可用性|


架构支撑：

```
┌──────────┐
│ 页面视图  │ ← 业务主导
├──────────┤
│ 流程逻辑  │
├──────────┤
│ 数据模型  │
└──────────┘
   ↑
[业务]: 综 / 餐 / 酒 / 各自页面视图 + 流程逻辑 + 数据模型
```

#### 2.3 数据模型 - 客户

||||
|---|---|---|
|POI、VPOI、供应商、自定义客户|范围、基本属性、门店级、品牌|自定义分级、分级标准|


识别共性与差异，隔离易变与不变：

||||
|---|---|---|
|共性|资源类型|资源|
|差异|元数据|标签|


- 通用性：统一客户实体，简化模型；统一标签实体，统一分级属性
- 扩展性：标签支持自定义分级维度；元数据支持业务差异信息
到店业务客户模型：
- 到餐：分组标签、品质、城市、状态、行政区、品牌
- 到综：自定义分组、POI、品质、城市、状态、行政区、品牌
- 住宿&度假：VPOI、自定义客户、供应商
#### 2.4 数据模型 - 客户轮转模型

多门店打包轮转 vs 多业务打包轮转

- 高频场景（30w/天）：客户 + 业务 + 私海 → 销售
- 三维模型分配复杂度：M × N（POI × 业务）
- 低频场景（5次/周）：客户 + 业务 + 轮转组 → 私海 → 销售，二维模型分配复杂度：1（轮转组）
方案描述（通用性）：轮转组实体，支持到店多门店、多业务打包轮转模式
||||
|---|---|---|
|到餐|单门店、多门店|单业务（未来会有多业务）、单业务、多业务|
|到综|||
|酒旅|单门店、单供应商|单业务|


#### 2.5 模型扩展 - 元数据

经典元数据模式（Salesforce CRM）：

||||
|---|---|---|
|Objects（对象定义）|Data（对象数据表，val1...val500）|Index（数据索引表）|
|Fields（字段定义）||uniqueId（唯一索引表）|
|||relationship（关系表）|


到店 CRM 元数据模式：

||||
|---|---|---|
|Template（模板定义）|Activity_Data（索引字段 val:json）|relationship（关系表）|
|Fields（字段定义）|SignIn_Data（索引字段 val:json）||


迭代升级：牺牲部分灵活度，换取稳定性与易用性

||||
|---|---|---|
|优点|变更仅需 DML（开发成本=0），高灵活度|① data 表与索引表融合，降低写入复杂度；② data 表实体化，节约存储、沉淀模型、降低理解成本|
|缺点|data 表与索引表分离，写入压力大；data 表结构空间浪费，理解成本高|变更需 DDL，成本 0.5pd（频率低，1次/半年）|


#### 2.6 流程逻辑 - 规则

问题：CRM 系统内部有大量业务规则，规则计算与业务代码耦合，扩展性差

规则抽象：规则 = f(因子, 因子, 因子, 因子)

规则流转：

资源池 ─入海规则→ 公海 ─战区划分规则→ 战区 ─自动分配规则→ 私海 ─轮转规则→ 销售

示例：
- 入海规则：品类 in (住宿、门票...) && 城市 in (北京、上海...)
- 战区划分：品类 = 餐饮 && 城市 = 北京 && 标签 = 'xx'...
- 自动分配：广告 = 在线 && 投放 > 30 天...
- 轮转：未拜访天数 > 30 天 && 未合作...

规则抽象：

|||||
|---|---|---|---|
||||与/或/非|


#### 2.7 流程逻辑 - 规则平台

架构：

```
平台使用方: 资源、战区、私海、工单、通知...
   ↑
┌────────────────────────────────┐
│ 规则配置: 规则 + 因子 + 因子... │
│ 表达式引擎 + 复杂事件处理引擎   │
│ 取数服务 + 事件预处理            │
└────────────────────────────────┘
   ↑
外部系统: 供应链、产品中心、客户平台、PDC、数据中心
```

核心思路：规则开发过程转化为"规则 + 因子取值的配置过程"

方案描述：
- 通用性：规则统一，适用 CRM 内各类场景；因子复用，不同规则可复用
- 扩展性：规则因子可视化配置；支持 HTTP/RPC 外部因子配置获取

#### 2.10 应用架构 - 服务集成

||||
|---|---|---|
|分-总模式|APP → 业务API → 业务服务 → 平台服务|业务重、平台轻、平台管控弱|
|总-分模式|APP → 业务API → 平台服务 → 业务扩展|平台扩展粒度粗|
|插件模式（推荐）|APP → 业务API → 平台服务 → SPI → 业务插件（业务平台）|平台强管控，扩展粒度细|


#### 2.11 应用架构 - 服务分层

分层原则：关注点分离 + SOLID 原则

|||
|---|---|
|接入层|关注用户展示，不关注业务逻辑（web 网关、鉴权、限流、降级）|
|应用层|关注业务用例、活动、流程（Service Facade 模式，编排、组合领域服务）|
|领域层|关注业务逻辑实现；按业务功能拆分服务（SRP）；扩展点、插件支持业务定制（OCP、DIP）|
|基础设施层|关注通用技术能力，不关注业务（数据访问、缓存、消息、配置）|


数据传递：
- 接入层 → 应用层：DTO
- 应用层 → 领域层：DTO
- 领域层 → 基础设施层：DO
- 接入层返回：VO

#### 2.12 应用架构 - 插件化 - 扩展点路由

扩展点坐标：(Tenant_ID, BizCode, Activity_Code)

- X 轴 = 租户
- Y 轴 = 业务
- Z 轴 = 业务活动
业务活动 = 用例，如：门店信息变更、战区变更
路由匹配优先级（高 → 低）：
1. 业务活动实现
2. 业务实现
3. 租户实现
4. 平台默认实现

#### 2.13 应用架构 - 插件化 - 隔离

|||
|---|---|
|开发时|代码仓库隔离（综插件仓库、餐插件仓库、X 插件仓库、平台公共仓库）|
|部署时|单链路独立发布（链路 1-A 租户、链路 2-B 租户...）|
|运行时|类加载隔离、容器隔离（自定义类加载器、平台容器、平台公用 jar）|

### 第三部分 · 供应链平台

#### 3.1 平台化实践 - 挑战

|||
|---|---|
|涉及范围|业务多、系统多、数据量大；非标，差异大|
|协作障碍|多团队，跨地域；基础设施不统一|
|约束|需求迭代频繁；质量风险高|


整体策略：新建平台，业务优先，平滑迁移，持续演进

#### 3.2 平台化实践 - 路径思考

三个阶段：

|||
|---|---|
|1. 功能收敛|通用功能（个性化基础/数据单元 + 应用服务）|
|2. 分层隔离|可扩展基础能力（可识别业务身份的个性化单元 + 领域服务基础/能力单元 + 流程节点编排单元）|
|3. 业务模式沉淀|业务模式（业务能力，包括若干产品功能单元 + 可识别业务身份的个性化单元 + 领域服务基础/能力单元 + 流程节点编排单元）|


#### 3.3 平台化实践 - 建设思路

5 大策略：
1. 统一概念
2. 统一基础设施
3. 分层治理，自底向上
4. 标准化抽象
5. 差异化扩展

架构（5 层）：

||||
|---|---|---|
|前端|业务主导|表单/表格、列表/详情、填单页|
|交互层|业务主导|供应链交互、C 端展示、下单交互|
|聚合层|平台主导|供给流程（扩展点、编排）、查询（扩展点）、售卖（扩展点）|
|领域层|平台主导|供应链模型（扩展模型）、商品模型（扩展模型）|
|存储层|平台主导|持久化数据（扩展字段）、持久化数据（扩展字段）|


#### 3.4 平台化实践 - 模型（商品复杂度）

商品种类：实物、团购、生活服务、预订、OTA
- 实物：<品类, SPU, SKU... 属性...>（商品占有权、属性关系复杂）
- 团购/生活服务/预订/OTA：<时间、空间、物品> 供应商 R1, R2...（商品使用权、售卖相关规则复杂）

玩法（X 维度）：打包、分销、预售、搭售、多售卖方式...

#### 3.5 平台化实践 - 模型（标准 vs 扩展）

|||
|---|---|
|供给过程模型|草稿、原型、快照（提交、发布）|
|核心模型|Product、资源、库存 / SKU、主体、价格、品类、交易规则|
|售卖过程模型|快照（交易查询）、库存流水|
|扩展模型|KV 扩展 → 自定义属性 → 配置式 / 自定义模型 / 自定义规则 → 声明式|

取决：行业标准与技术实现

|团购|名称、客户、门店|-|-|

#### 4.3 接入标准化

```
到店交易平台/各业务交易系统 ─结算指令→  │   │   ─结算数据→ 商家经营分析
                                      │到店结│
到店客户平台/各业务客户系统 ─结算规则→  │算平台│   ─结算数据→ BI 分析
                                      │   │   ─结算数据→ 财务报账
                              接入标准 │   │ 接入标准
```

核心要点：结算指令、结算规则、结算数据
结论：平台标准的接入能力，是新业务可以自助接入的前提

#### 4.4 接入指令标准化

订单结构：

```
结算维度 (1) ─┐
            ├─→ 订单信息 (1, 1, 1)
结算维度 (n) ─┘           ├── 支付信息 (n)
                          ├── 营销信息 (n)
                          └── 商品信息 (n)
```

核心原则：
- 指令结构不变，拓展属性根据业务变化
- 结算指令标准化：业务接入标准的结算指令（不是结算适配各交易模型）
- 指令结构：标准的，不易变
- 子信息组成：支持灵活扩展，EAV、扩展属性等

#### 4.5 接入规则标准化

业务 A 结算规则：

||||
|---|---|---|
|结算周期|7 天、14 天...|商家、商家+门店|
|结算币种|人民币、港币|商家|
|结算时机|销售结算、消费结算|商家、商家+门店、商家+门店+合同|


业务 B 结算规则：

||||
|---|---|---|
|结算周期|7 天、14 天...|商家、商家+门店|
|签约主体|公司 A、公司 B...|商家|
|自动确认|{"是否自动确认": true, "自动确认天数": 7}|商家、商家+门店|


规则模型定义：

```
规则维度 1──N─→ 结算规则
                ├── 1──N─→ 结算规则模型定义
                ├── 1──N─→ 结算规则变更历史
                └── 1──N─→ 结算规则模型字段定义
```

核心价值：
- 灵活支持多业务规则维度的差异
- 支持差异化的结算规则
- 规则内容支持多样化

#### 4.6 结算模式标准化

||||
|---|---|---|
|平台分佣|用户购买 → 平台 → 商家履约 → 平台结算|平台主导|
|预付包销|用户购买 → 平台（预付）→ 商家履约|挖掘供给、预付包销|
|分销|用户购买 → 分销商（预付）→ 平台 → 商家履约 → 平台结算|挖掘需求、分销|


原则：平台没有那么强势的时候先预付报销
