## Skill 知识库完全指南



本文档系统梳理了 Skill 在 AI 领域的概念定义、组成结构、工作原理、最佳实践及相关生态，适合作为个人或团队构建 AI 技能知识库的参考手册。

### 一、什么是 Skill

#### 1.1 核心定义

Skill 是一套标准化规范，用于定义 AI 代理（Agent）可执行的能力单元。它类似于 npm 包之于 JavaScript 生态，或 PyPI 包之于 Python 生态——但专为 AI 代理之间的发现、加载和执行而设计。每个 Skill 通过 SKILL.md 文件描述其功能、触发条件和执行逻辑，使 AI 模型能够理解、发现并调用外部功能。

#### 1.2 Skill 的核心价值

|||
|---|---|
|统一描述|让不同 AI 模型和框架能以统一的方式理解技能的功能、输入输出|
|动态发现|AI 代理可以自动发现并注册可用的技能|
|标准化调用|定义技能调用的接口、参数验证、错误处理等|
|跨平台兼容|使技能能在不同 AI 生态（如 Claude、GPT、开源模型）之间复用|
|知识沉淀|将零散的技术知识点、项目经验、学习路径进行系统化归类和关联|


#### 1.3 Skill 与 Prompt 的区别

||||
|---|---|---|
|形式|一段自然语言指令|封装好的模块（含 Prompt、工具、逻辑）|
|复用性|每次需要重新编写或调整|可以一键调用，多次复用|
|复杂度|单轮或多轮对话|可能包含多步推理、工具调用、条件分支|
|本质|写在对话上下文的指令，一次性，随对话消失|独立封装的规则文档，工具动态加载，可复用|


用"做菜"来类比：Prompt 是口头告诉 AI"做一道鱼香肉丝"；Skill 是给 AI 一本《鱼香肉丝标准化菜谱》，配好调料包和厨具。

### 二、SKILL.md 格式规范

#### 2.1 文件结构

SKILL.md 是技能的核心描述文件，遵循 YAML 前置元数据（Frontmatter）+ Markdown 正文 的结构：

```markdown
---
name: my-skill
version: 1.0.0
description: 技能的功能描述及触发条件
tags: [category, use-case]
---

## 技能名称

### 操作步骤
Agent 需要执行的具体步骤和规则。
```

#### 2.2 Frontmatter 字段详解

|||||
|---|---|---|---|
|name|string|是|技能的唯一标识符，小写字母+连字符，与目录名一致|
|description|string|是|技能功能描述和触发场景，是 Agent 决定是否加载的关键依据|
|version|string|否|语义化版本号|
|tags|string[]|否|搜索标签，便于分类|
|author|string|否|技能作者或组织|
|license|string|否|SPDX 许可证标识符|
|repository|string|否|源代码仓库 URL|
|agents|string[]|否|兼容的 Agent 列表|
|env|object[]|否|所需环境变量声明|


description 编写要点：不超过 1024 字符，包含 功能 + 触发场景 + 关键能力 三部分，使用具体、可操作的描述，避免模糊表述。









示例：

> description: 生成符合规范的周报，无需用户手动排版。当用户提到"写周报""生成周报""周报模板"时使用。
> ```

#### 2.3 Body 内容编写指南

Body 部分使用标准 Markdown 编写，推荐采用以下章节组织：



```markdown
### 概述

技能功能的简要说明。

### 前提条件

运行前需要满足的条件（如环境变量、工具链等）。

### 操作步骤

Agent 需要遵循的具体指令，使用数字编号分步说明。

### 规则与约束

Agent 必须遵守的安全规则和行为边界（使用 MUST / NEVER 关键词）。

### 验证检查清单

- [ ] 检查项 1
- [ ] 检查项 2
### 示例

输入/输出的具体示例，帮助 Agent 理解预期行为。

### 异常处理

预判常见失败场景及应对策略。

### 来源

记录知识的来源（URL、文档名称、对话等）。
```


#### 2.4 编写原则

- 使用 **祈使句**，直接给出指令（如"创建文件"而非"你应该创建文件"）
- 每条指令对应一个"可以独立验收的产出"
- 正文建议控制在 500 行以内，超出部分拆分到 `references/` 目录
- 包含具体的输入输出示例
- 使用 `MUST` 和 `NEVER` 明确行为边界

### 三、Skill 项目目录结构

#### 3.1 标准目录结构

一个完整的、可复用的 Skill 项目，通常会包含以下目录结构：




```
your-skill/
├── SKILL.md            # 【必需】核心技能文件
├── references/         # 【可选】按需加载的参考文档
│   ├── api-guide.md
│   └── workflow.md
├── scripts/            # 【可选】可执行脚本（Python、Bash 等）
│   └── helper.py
├── assets/             # 【可选】模板、字体、图标等静态资源
│   └── template.md
├── resources/          # 【可选】示例数据、JSON Schema 等
│   ├── examples.md
│   └── schema.json
├── skill.toml          # 【可选】机器可读清单文件
├── lifecycle.yaml      # 【可选】生命周期配置
├── README.md           # 【可选】人类可读的项目说明
└── LICENSE             # 【可选】许可证文件
```


#### 3.2 各目录说明

| 目录/文件     | 必需性 | 核心职责                 | 加载策略             |
| ------------- | ------ | ------------------------ | -------------------- |
| `SKILL.md`    | 必需   | 元数据 + 核心指令        | 匹配时加载           |
| `references/` | 可选   | 参考文档、规范、API 手册 | 按需读取             |
| `scripts/`    | 可选   | 确定性可执行代码         | 按需执行，不占上下文 |
| `assets/`     | 可选   | 模板、图片等静态资源     | 按需引用             |
| `resources/`  | 可选   | 示例数据、Schema         | 按需引用             |
| `skill.toml`  | 可选   | 机器可读元数据清单       | 解析时加载           |



#### 3.3 核心规则

- `SKILL.md` 必须严格区分大小写，不可写成 `skill.md` 或 `SKILL.MD`
- 文件夹名必须使用 kebab-case（小写字母加连字符）
- 只有 `SKILL.md` 是必需文件，其余均为可选

### 四、渐进式披露设计思想

Skill 设计了一套三层分级加载机制，以平衡效果和效率：

| 层级   | 内容                                 | 加载时机       | 占用 Token  |
| ------ | ------------------------------------ | -------------- | ----------- |
| 第一层 | `name` + `description`（元数据）     | 启动时始终加载 | ~100 tokens |
| 第二层 | `SKILL.md` 正文                      | 任务匹配时加载 | 数 KB       |
| 第三层 | `scripts/`、`references/`、`assets/` | 需要时按需加载 | 按需        |



这种机制避免了在对话开始时将所有内容塞入上下文，实现了 **上下文不膨胀、加载更精准、支持海量信息** 的效果。

### 五、Skill 的工作原理

#### 5.1 调用逻辑

Agent 执行 Skill 的完整流程如下：

1. **意图匹配**：Agent 聆听用户需求，扫描所有 Skill 的元数据，寻找最匹配的 Skill
2. **读取手册**：找到匹配的 Skill 后，Agent 读取 SKILL.md 正文，研究详细的执行步骤和注意事项
3. **按需执行**：根据手册指引，Agent 开始工作，需要时从工具箱中拿出脚本或工具完成具体操作
4. **反馈结果**：任务完成后，Agent 向用户汇报最终结果，或在遇到困难时及时请教

#### 5.2 触发条件

当用户提问命中预设的主题，系统自动调用 `read_skill` 加载对应技能。只要用户问这类问题，就不再靠模型自由发挥，全部读取 SKILL.md 里写好的官方口径回复，防止模型编造错误的产品规则。

### 六、Skill 的分类

| 分类           | 说明                 | 典型示例                                    |
| -------------- | -------------------- | ------------------------------------------- |
| 任务型 Skill   | 完成特定单次任务     | 邮件起草、会议纪要生成、周报撰写            |
| 角色型 Skill   | 赋予 AI 特定职业身份 | 法律顾问、心理咨询师、投资分析师            |
| 工具体系 Skill | 绑定外部系统能力     | 数据库查询、Jira 工单创建、K8s 集群管理     |
| 流程型 Skill   | 多步骤复杂工作流     | 软件开发生命周期辅助（需求→设计→编码→测试） |
| 知识型 Skill   | 内置领域知识库       | 医学诊断辅助、法规合规检查、历史文献解读    |

### 七、Skill 的优缺点

#### 7.1 优点

- **输出稳定可控**：相同问题，输出高度一致，避免大模型幻觉乱编规则、政策、产品说明
- **维护方便**：修改 SKILL.md 文档，所有会话立刻生效，不需要重新训练模型
- **边界清晰**：明确什么能回答、什么拒绝回答，用于合规、客服场景非常合适
- **可复用**：一套规则多个会话复用，有明确触发条件
- **热插拔**：好的 Skill 系统应该让你运行时新增/禁用 Skill，不重启 Agent

#### 7.2 缺点

- **不够灵活**：被手册死死限制，超出文档范围的需求处理很差
- **依赖文档质量**：如果 SKILL.md 写的不全，就会出现回答残缺
- **属于提示工程方案**：不能解决模型底层能力缺陷

------

### 八、Skill 的构建流程

#### 8.1 构建步骤

创建一个高质量的 Skill 通常遵循以下步骤：

1. **需求定义** → 明确 Skill 要解决的痛点和使用场景
2. **知识采集** → 收集领域文档、规则、专家经验、案例库
3. **Prompt 工程** → 设计核心指令模板，包含角色、规则、输出约束
4. **工具集成** → 绑定必要的外部 API/数据库/脚本（如需要）
5. **测试迭代** → 用大量案例测试，调优指令和逻辑
6. **封装发布** → 打包成可一键调用的 Skill 模块

#### 8.2 编写高质量 Skill 的原则

- **单一职责原则**：每个 Skill 只专注解决一类问题，不要"大而全"
- **给例子（Few-Shot Prompting）**：直接给出清晰的输入输出示例，模型通过具体例子秒懂想要的格式、风格和行为
- **立规矩（Structured Instructions）**：定角色、拆步骤、画红线，明确告诉它"不能做什么"
- **造接口（Interface Design）**：像设计软件 API 一样，明确定义 Skill 的输入参数和输出格式
- **勤复盘（Iterative Refinement）**：把 Skill 当作产品来迭代，将 Bad Case 变成新的规则或反例补充到定义中

### 九、完整示例

以下是一个完整的 SKILL.md 示例，以一个**生成周报**的技能为例：


```markdown
name: weekly-report-generator
description: >
  自动生成符合职场规范的周报，无需用户手动排版。
  当用户提到"写周报""生成周报""周报模板"，
  或要求"总结本周工作""规划下周任务"时使用。
version: 1.0.0
author: AI 助手

### tags: [report, weekly, productivity]

## 周报自动生成技能

### 操作步骤

#### 步骤 1：获取用户核心信息

主动询问用户 3 个关键问题：

- 本周核心工作成果（3-5 条，每条简洁明了）
- 本周遇到的问题及解决办法（1-2 条，可选）
- 下周工作计划（3-4 条，明确具体动作）
#### 步骤 2：生成标准化周报

按照以下模板填充用户提供的信息：

【本周周报】

汇报人：（用户未提供则留空，提示用户补充）

汇报周期：（自动获取当前日期）

一、本周工作成果

- （填充用户提供的第 1 条成果）
- （填充用户提供的第 2 条成果）
二、本周问题与解决办法

- 问题：（用户提供的问题）
解决办法：（用户提供的解决办法）
三、下周工作计划

- （填充用户提供的第 1 条计划）
- （填充用户提供的第 2 条计划）
#### 步骤 3：优化与确认

- 检查格式是否符合上述模板
- 提示用户："周报已生成，可根据你的需求调整内容细节"
### 规则

- MUST：周报开头要有"汇报人"和"汇报周期"字段
- MUST：成果部分使用数字编号，每条不超过 50 字
- NEVER：不编造用户未提供的信息
- NEVER：不使用口语化表达
### 异常处理

- 如果用户提供的信息过于简略，温和提示用户补充具体内容
- 如果用户要求修改格式，按用户要求调整后再次确认
### 检查清单

- [ ] 是否包含汇报人和汇报周期？
- [ ] 成果是否用数字编号？
- [ ] 每个问题是否都有对应的解决办法？
- [ ] 是否有用户未提供但被编造的内容？
```
