### 一、hashCode 与常数 31

#### 1.1 为什么选择 31 作为生成 hashCode 的系数？

① 31 是一个质数（素数）



质数：大于 1 的自然数中，除了 1 和自身外无法被其他自然数整除。

使用质数作为系数，能让哈希地址分布更均匀，尽量减少哈希冲突。冲突越多 → hash 链越长 → 查询效率越低。

② 31 的二进制形态友好（31 = 11111₂）

- 只占用 5 bits，是"尽量长且不易溢出"的系数
- 若选择大于 11111₂ 的数，乘法很容易溢出，导致数据丢失
③ 乘法可优化为移位

i * 31 == (i << 5) - 1

很多 JVM 已做相关优化，用移位 + 减法替代乘法，性能更优。

#### 1.2 对 HashMap 使用的启示

- 链表数很多 → 数组初始化长度不合理（默认扩容逻辑导致）
- Map 很大 → 事先未定义好初始化长度
- 经验公式：存储 10000 条数据时，容量取 10000 × 1.34 = 13400，向上取2 的幂次方 = 16384 作为初始容量即可（不需要按扩容到 20000 预留）
### 二、线性与非线性

||||
|---|---|---|
|线性关系|量之间成比例|十枚橘子的价钱 = 一枚价钱的十倍|
|非线性关系|"所得非所望"，不成比例|批发价格：一箱橘子总价 < 单价 × 个数|




非线性中重要的观念是「反馈」——折扣的大小反过来影响顾客购买的数量。

### 三、常用散列函数（4 种）

|||||
|---|---|---|---|
|4.1|平方取中法|取关键字平方后的中间几位作为哈希地址|中间位与关键字各位相关，分布较好；适合关键字位数较多时|
|4.2|除余法（除留余数法）|hash(key) = key % p，取余数作为地址（p 一般取不超过表长 m 的质数）|最简单常用；p 的选择影响冲突率|
|4.3|相乘取整法|hash(key) = ⌊m × (key × A % 1)⌋，关键字乘常数 A 后取小数部分再乘表长|对 A 的选择不敏感，几乎适用于所有关键字|
|4.4|随机数法|hash(key) = random(key)，用随机函数生成地址|适用于关键字长度不等的情况|


### 四、哈希冲突与再散列处理（4 种）

开放寻址类：

|||||
|---|---|---|---|
|5.1|开放地址法|冲突时按探测序列（线性/二次/再哈希探测）寻找下一个空位|所有元素存于表中，表不能填满；二次探测可减少聚集|
|5.4|建域法（建立公共溢出区）|为所有冲突的关键字单独建一个溢出区存储|查找主表不冲突即一次命中；冲突多时溢出区退化|


链式 / 多函数类：

|||||
|---|---|---|---|
|5.2|拉链法（链地址法）|同义词挂在同一链表（桶）下，冲突只插链表|Java HashMap 采用（链表 + 红黑树优化）；简单、删除方便|
|5.3|多哈希法|设计多个哈希函数，第一个冲突时依次换下一个|增加计算开销，但显著降低冲突概率|




参考：二次再散列法 — 百度百科

### 五、小结

- 常数 31：质数 → 分布均匀减少冲突；5 bits → 避免溢出；(i << 5) - 1 → 可被 JVM 优化
- 散列目标：让地址尽可能均匀分布，冲突越少查询效率越高
- 冲突处理：开放地址 / 建域（表内解决） vs 拉链 / 多哈希（表外/多函数解决）
- 工程实践：使用 HashMap 时预估容量，用 (size / 0.75) + 1 或 size × 1.34 向上取 2 的幂初始化，避免频繁扩容
